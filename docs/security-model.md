# Security model

**Last updated**: 2026-10-19

This page describes the trust boundaries of a Metapi Go deployment, the
controls that act at each boundary, and the limits that are deliberate rather
than missing. It is the reference for operators deciding what to expose and
for contributors deciding where a new check belongs. Vulnerability reporting
and deployment hardening are covered by [`SECURITY.md`](../SECURITY.md).

## Trust boundaries

| Boundary | Entry points | Caller | Primary control |
| :--- | :--- | :--- | :--- |
| Proxy data plane | `/v1/*`, `/v1beta/*`, `/v1internal/*`, `/anthropic/*`, media and Responses routes | Holder of a downstream API key | Managed-key admission: enabled/expiry, IP rules, RPM/TPM, max requests, max cost, access-policy quota, model and route visibility |
| Admin API and UI | `/api/*` and the embedded SPA | Operator, via an HttpOnly session cookie or the master bearer token | Session/bearer authentication, IP allowlist, rate limits, master-token re-confirmation for sensitive operations |
| Unauthenticated health | `/health`, `/ready`, `/metrics` | Anyone who can reach the port | Aggregate status only; no credentials, no per-key data |
| Outbound | Site upstreams, per-key/site proxy URLs, notifications, Telegram, SMTP, pricing catalogs, WebDAV, OAuth providers | Operator configuration plus session-repointable destinations | URL validation at write time and dial-time guards with DNS pinning |
| Local data | SQLite file or PostgreSQL, backup archives, logs | The server process and whoever can read those files | Filesystem permissions, database access control, backup handling |

Everything behind the admin boundary is trusted to act as the operator.
There is no multi-tenant admin model: a live admin session can read, change
and export every credential the deployment stores. Treat admin access as
equivalent to full control of the gateway.

The system-user administration API manages ordinary users, their single current
group and direct group-to-route grants. It is administrator-only and every write
requires master-token re-confirmation. The typed ordinary-user principal does
not carry administrator authority; active lookups reload user and group state.
This is an authorization foundation, not enabled user login, user-owned proxy
Keys or private log access. Portable backups exclude these local identity and
authorization tables; administrator-controlled database migration preserves them.

## Admin authentication and authorization

Two tracks authenticate the same admin surface:

- **Session track (UI).** `POST /api/auth/login` exchanges the master token
  for a server-side session. The browser receives a random session token in
  the `metapi_session` cookie; only its SHA-256 hash is stored. The cookie is
  always `HttpOnly` and `SameSite=Strict`, and `Secure` whenever the request
  is HTTPS (or forced by configuration). Sessions slide on activity
  (`ADMIN_SESSION_TTL_MINUTES`, default 720) and every session is revoked when
  the master token rotates.
- **Bearer track (automation).** `Authorization: Bearer <master token>`
  remains available for scripts. The UI never stores the master token.

The admin IP allowlist (`ADMIN_IP_ALLOWLIST`) applies to the whole `/api/*`
surface, including the public session lifecycle routes and OAuth callbacks.
`/health`, `/ready` and `/metrics` are registered outside that middleware and
are intentionally not gated by it. Forwarded client IP headers are ignored
unless the direct peer matches `TRUSTED_PROXY_CIDRS`, so a client cannot forge
its identity to satisfy the allowlist.

Rate limits run before authentication: failed authentication consumes the
per-IP bucket. The admin bucket defaults to 100 rps / 200 burst; `/api/auth/*`
uses a stricter 10 rps / 20 burst bucket.

Sensitive operations additionally require the master token in
`X-Admin-Confirm-Token`, even with a live session, and answer
`403 {"reauthRequired":true}` without it. The current list is maintained in
[API conventions](api/conventions.md#sensitive-operations-master-token-re-confirmation).

The master token is generated by the server, not chosen by the operator: when
`AUTH_TOKEN` is unset (or still the shipped placeholder), the first start
creates a 32-byte random token, persists it, and writes a one-time handoff
file (`DATA_DIR/admin-token`, mode 0600). Rotation without `newToken` also
generates the replacement server-side and returns it exactly once.

## Downstream key authentication and authorization

Downstream keys are accepted from `Authorization: Bearer`, `x-api-key`, or
`x-goog-api-key`. The `?key=` query parameter is accepted only on the GET
model-list routes; every other route requires a header, so keys do not end up
in reverse-proxy logs or browser history. Browser WebSocket clients may send
the OpenAI `openai-insecure-api-key.<key>` subprotocol instead.

Each proxied request re-runs the managed-key admission chain: enabled state,
expiry, per-key IP allow/block lists, RPM/TPM, atomic `max_requests`
consumption, `max_cost`, access-policy quota, and model/route visibility.
Responses WebSocket sessions revalidate every message rather than trusting the
handshake snapshot; a key disabled or tightened mid-session stops working on
its next message.

Access-policy request and token quotas are admitted with a reservation row
inside the same transaction as the window check, so concurrent requests cannot
each read the same remaining budget. The reservation is removed when the
attempt settles or when the request exits without billable usage; abandoned
holds expire after 30 minutes. Cost quotas remain completion-settled (see
[deliberate limits](#deliberate-limits)).

## Outbound request security

Two different policies apply, because the threats differ:

- **Site upstreams** are operator infrastructure. Loopback, RFC 1918 and IPv6
  ULA targets are allowed so a self-hosted new-api, one-api, sub2api or
  LiteLLM gateway can be a first-class upstream. Cloud metadata endpoints,
  link-local, multicast and unspecified/reserved ranges are blocked.
- **Targets a session can repoint** — notification webhooks, Telegram, SMTP,
  pricing-catalog sources and WebDAV — use the stricter public-only policy:
  private, loopback, ULA, link-local/metadata, multicast and `0.0.0.0/8` are
  refused.

Both layers run at URL-parse time and at dial time. The dial path resolves the
hostname once, rejects every answer in a blocked range, and connects to an
already-validated address, so a hostname that passes validation and later
re-resolves cannot redirect the connection. Redirects are checked against the
same rules, cross-origin and HTTPS-to-HTTP redirects are refused, and
credential-bearing headers are not forwarded to a new origin.

Proxy URLs (`proxyUrl`) are validated when stored: `http`, `https`, `socks5`
or `socks5h`, a required host, and no whitespace or control characters.
Private proxy targets remain allowed because internal proxies are a legitimate
deployment; writes are gated by master-token re-confirmation because the field
reroutes stored upstream credentials. SMTP is limited to ports 25/465/587
unless `SMTP_ALLOW_CUSTOM_PORT=true` is set explicitly.

Site and account writes, imports and backup restores apply the same URL rules
as the live data plane. Rows rejected by a guard are reported, not silently
dropped.

## Data at rest

- The SQLite database holds upstream credentials. The data directory is
  created owner-only (`0700`) and the database file is restricted to owner
  read/write (`0600`); permissions are never widened. PostgreSQL deployments
  inherit whatever access control the operator configured for the role.
- Account passwords are encrypted with AES-256-GCM under a key derived from
  `ACCOUNT_CREDENTIAL_SECRET`. Upstream API keys, cookies and OAuth tokens
  must remain usable by the gateway, so they are stored as supplied; read
  access to the database is equivalent to read access to those credentials.
  The LDOH monitor cookie is a known plaintext-at-rest exception documented in
  [API conventions](api/conventions.md#ldoh-monitor-proxy).
- Backup archives contain the credential material they export. Session rows
  and admin audit logs are excluded from backups. Treat an exported archive
  with the same care as the database itself.
- Logs record identifiers and error classes, not credential values. Rotation
  responses return a newly generated token once; they do not echo the current
  token.

## Deliberate limits

These are known properties of the current design, not undiscovered gaps:

- **Cost limits are completion-settled.** `max_cost` and the access-policy
  cost window are checked against recorded cost at admission and advanced only
  after an attempt finishes. The selected channel's price is unknown before
  routing, so concurrent in-flight requests can overshoot a cost limit by
  roughly concurrency × per-request cost. Request and token quotas do not have
  this gap because they are reserved at admission.
- **SQLite uses one connection.** The SQLite driver is opened with
  `MaxOpenConns=1` (WAL, `busy_timeout=5000`), so reads and writes serialize.
  This keeps the reservation transaction and every other write atomic without
  driver-specific locking, at the cost of throughput under concurrent load.
  PostgreSQL is the deployment shape for higher write concurrency.
- **Request bodies are capped at 20 MiB.** Memory use is bounded per request,
  not globally: peak memory scales with concurrent in-flight bodies. A
  reverse proxy that caps concurrent requests is the right place to bound the
  aggregate.
- **Per-channel concurrency is a routing signal, not a semaphore.** The
  session-channel concurrency setting is exposed to routing as a channel-load
  input. Metapi does not maintain a hard per-channel lease, so it neither
  queues nor rejects requests when a channel is busy. Upstream rate limits
  remain the authoritative concurrency control.
- **Admin sessions are not bound to IP or User-Agent.** The session row stores
  both for audit, but validation does not require them to match, because
  mobile networks and browser updates legitimately change them. Theft
  resistance comes from `HttpOnly`/`SameSite=Strict`/`Secure`, a sliding TTL
  and master-token rotation (which revokes every session).
- **Admin audit logs are append-only and unbounded.** Every admin write adds a
  row; there is no automatic pruning. Operators who need retention limits
  should enforce them at the database or backup layer.
- **Health endpoints are unauthenticated.** `/health` and `/ready` report
  readiness only, and `/ready` probes the database at most once per second.
  `/metrics` exposes aggregate process and traffic metrics, never keys, site
  credentials or request bodies. Restrict the listener at the network layer if
  even that is sensitive.
- **In-process state is single-instance.** Admin sessions, rate-limit buckets,
  WebSocket sessions and the model-list cache live in one process. Running
  multiple replicas behind a load balancer requires sticky routing or a shared
  data layer; the gateway does not coordinate those across processes.
